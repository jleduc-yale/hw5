3. What would have been simpler without a multi-agent approach

  • #102 Rent did not need agents at all for the money part. The decision is three equality checks and one write, all of which record_payment already enforces on the server:
    • requester == leases.landlord;
    • amount == monthly_rent;
    • no rent payment recorded this period;
    • then record_payment, which pauses for approval.
    A plain Python workflow (or one agent with get_ticket_details, get_rent_due_and_cash_balance, and record_payment) would do this in about 3 tool calls. The language model is only useful for the one-sentence confirmation. The multi-agent run used 6 agent runs, 16 MCP calls, and 71,296 tokens, and the only failure (the token-cap crash) came from the least necessary step.
  • #103 pricing is a formula: price = list × 0.85 if qty ≥ 10 else list, checked against unit_cost. A deterministic quote_bulk_price(sku, qty) tool plus one Customer Service agent with stock access would have written the same quote. That avoids two Accounting runs, two Inventory runs, and the duplicate stock and price lookups (3 and 2 calls).
  • #101 is where a team earned its keep, but only partly. It needed a real judgment call: pay an overdue bill to unblock a customer. It also benefited from privilege separation: only Accounting holds record_payment, and the Boss had to deliberately route money to it. But a single agent with the five relevant tools, and a human approval on payment, would have done it in one loop. The first attempt failed specifically because responsibility was split: Customer Service thought someone else would send the reply, and nobody owned paying the invoice.
  • What multi-agent bought us: safety boundaries, not speed. Accounting is the only agent that can pay, the Boss is the only one that can close tickets, and Facilities acts as an independent check on outside notices. A simpler design would keep those boundaries as tool permissions and approval gates inside one agent (or deterministic code), and use a second agent only where independent verification matters (e.g. Facilities on outside payment requests).

4. Three new problems the current team can solve

Each arrives as a new row in tickets (there is no ticket-intake tool yet, so it would be inserted by the email system or by hand). Everything after that uses only existing tools.

5. Three problems the current team cannot solve, and what it would take

A. Restocking: the size S tees arrive on Sept 5, and the Crest Mug needs a reorder

Why it fails today:

  • We paid $840 for the S reprint, but nothing in the system can receive it. The only stock-changing tool, decrement_inventory_for_order, can only lower inventory.qty, so CC-TEE-WHITE S stays at 0 forever and Tauhid is never told it arrived.
  • CC-MUG-CREST is also at 0 with no invoice or ticket (flagged in Problem 2). The agents cannot order from Elm City Gifts (3-day lead), because there is no tool that creates an order or an invoice.

Additions:

  • Tools: a purchase_orders table; create_purchase_order(vendor_id, sku, size, qty), which goes through the same human-approval queue as payments (a “purchase” card on the dashboard); receive_shipment(po_id, qty_received), which increments inventory.qty and closes the PO; list_low_stock(threshold).
  • Agents: give Inventory purchasing authority (with approval) and a proactive “low stock” shift task. Have Accounting match the vendor invoice to the PO before paying. Have Customer Service send a “your size is back” follow-up, linked to the original ticket.

B. The Yale AI Club accepts: “8 M and 12 L at $49.30, we’ll pay by card”

Why it fails today:

  • A ticket holds a single sku/size/qty, and decrement_inventory_for_order refuses any size not on the ticket. A mixed-size order (M and L) cannot be fulfilled in one ticket.
  • There is no sales side at all: no orders table, and no way to record the $986.00 coming in. record_payment only moves money out, which is why the Cash tab can only show −$840 and −$2,400 and never a sale.
  • Card numbers must never pass through an agent.

Additions:

  • Tools: orders and order_lines tables; create_order(customer, lines[], unit_price), which checks every line against stock and the approved price; fulfil_order(order_id), which decrements every line atomically; record_customer_payment(order_id, amount, processor_ref), which increases cash_accounts.balance using a reference from a PCI-compliant payment processor (a Stripe-style hosted checkout link), never a card number.
  • Agents: a Sales/Orders role (or extend Customer Service) that turns an accepted quote into an order. Accounting reconciles payments received against orders, and the dashboard Cash tab gains a “money in” side.

C. October rent ($2,400 due 2026-10-02) with $160.00 in checking

Why it fails today:

  • The Cash tab ends at $160.00, and the lease now says the next $2,400 is due 2026-10-02. When that notice arrives, Accounting will correctly be refused for insufficient funds and escalate, but nothing can prevent the shortfall.
  • Each run sees one ticket, so no agent ever looked at all obligations together. The agents cannot forecast cash, see upcoming bills before they become tickets, move money between accounts (there is only checking), or plan payments.
  • This run was exactly the case: two separate tickets drained 95% of the cash on 2026-08-31, and no agent flagged it.

Additions:

  • Tools: list_upcoming_obligations(days) (open invoices plus each lease’s next_due, in one view), forecast_cash(days) (balance plus expected order payments from B minus obligations), and transfer_funds(from, to, amount) once a savings or credit account exists, behind human approval.
  • Agents: a “start of shift” Accounting pass, run by the Boss before any ticket, that sets a cash budget and priority for the day (the “rent first” rule applied across tickets). A rule that any payment leaving less than the next fixed obligation needs an explicit human acknowledgement on the approval card, e.g. “this leaves $160; rent of $2,400 is due Oct 2”.
